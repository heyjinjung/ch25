> 🚀 실개발 즉시 착수 가이드 (요약)
> 1) 모델/마이그레이션: `OpsDailyLog(date PK, theme_title, manager_id, status, summary_md, kpi_snapshot JSON)` + `OpsLogEntry(id, daily_log_date FK, timestamp, category, action_code, target_model, target_id, meta_data JSON, is_automated, actor_id, ref_id UNIQUE)` 인덱스(`daily_log_date`, `timestamp`, `ref_id`).
> 2) 스키마: Pydantic `OpsLogCreate`, `OpsLogEntryOut` 정의(`meta_data` Dict[str, Any], `ref_id` optional but unique on create).
> 3) 엔드포인트 (관리자 인증 필수):
>    - `POST /admin/api/ops/log-entry` (ref_id 멱등: 존재하면 200 + 기존 데이터 반환)
>    - `GET /admin/api/ops/log-entry?date=YYYY-MM-DD` (필터: category?, action_code?, actor_id?)
> 4) 로직: 일지 자동 생성(date not exists → create `OpsDailyLog(status=DRAFT)`), `actor_id=get_current_admin_id`, `timestamp=utcnow`, `is_automated` 기본 False.
> 5) 보안/밸리데이션: `ref_id` uniqueness, meta_data JSON Schema validate(`meta_type` 파라미터 또는 action_code prefix 기반), PII 마스킹, 권한(Role gate) + 파괴적 액션 Confirm은 FE 책임.
> 6) 테스트(최소): create 멱등(ref_id), list by date, 권한 401/403, meta_data 밸리데이션 실패 422.

### 백엔드 실개발 착수 세부 단계 (FastAPI)
- **모델/마이그레이션**
	- 파일: `app/models/ops_log.py` → `OpsDailyLog`, `OpsLogEntry` 정의; `app/models/__init__.py`, `app/db/base.py`에 import 추가
	- 필드: 설계서 명세대로 + 인덱스(`daily_log_date`, `timestamp`, `ref_id UNIQUE`), FK `daily_log_date` → `OpsDailyLog.date`
	- Alembic: `alembic/versions/<timestamp>_ops_log_tables.py` 생성, 업/다운 모두 작성

- **Pydantic 스키마** (`app/schemas/ops_log.py`)
	- `OpsLogCreate`: `date`, `category`, `action_code`, `target_model`, `target_id?`, `meta_data`, `ref_id?`, `is_automated?`
	- `OpsLogEntryOut`: DB 필드 + `id`, `timestamp`, `actor_id`

- **서비스/리포지토리** (`app/services/ops_log_service.py` 예시)
	- create_log_entry: `ref_id` 존재 시 기존 반환(200), 없으면 생성
	- ensure_daily_log(date): 없으면 `status=DRAFT`로 생성
	- list_log_entries(date, filters): date 필수, category/action_code/actor_id 옵션

- **라우터** (`app/api/admin/routes/admin_ops_log.py`)
	- prefix `/admin/api/ops`, deps `get_current_admin_id`
	- `POST /log-entry`: body=OpsLogCreate, 응답=OpsLogEntryOut, 200 on idempotent, 201 on new
	- `GET /log-entry`: query `date` required, filters optional, 응답 List[OpsLogEntryOut]
	- 에러: 401/403 권한, 422 validation, 409(선택) 대신 200 멱등 반환

- **권한/보안/밸리데이션**
	- admin deps 강제; Role gate는 기존 admin deps 준수
	- `ref_id` UNIQUE 제약 + DB 인덱스; meta_data JSON Schema 검증(액션별 스키마 맵 or meta_type 파라미터)
	- PII 마스킹: 전화/계좌/주소 패턴 마스킹 또는 저장 차단
	- Immutable 원칙: 수정/삭제 API 없음, CORRECTION 로그로만 보정(추후 필요 시 별도 엔드포인트)

- **테스트 (tests/test_admin_ops_log.py)**
	- `POST /log-entry` 신규 201, 동일 ref_id 재요청 200 멱등 동작
	- `GET /log-entry?date=...` 리스트 반환, 필터 동작 검증
	- 권한: 미인증 401, 일반 사용자 토큰 403 (admin deps)
	- meta_data 검증 실패 시 422

### 프론트 실개발 착수 세부 단계 (React/Vite)
- **API 클라이언트/타입**
	- 파일: `src/api/adminOpsLog.ts`(신규) 또는 기존 adminApi 확장 → `postLogEntry`, `getLogEntries`
	- 타입: `OpsLogCreate`, `OpsLogEntry`를 BE 스키마와 1:1 매핑 (action_code, category, target_model Enum 맞추기)
	- 요청/응답: axios/fetch 기반, 멱등(ref_id) 재시도 시 200 허용

- **Query Key / 상태 관리**
	- 파일: `src/queryKeys/opsLogKeys.ts` → `list(date)`, `detail(id)`, `dailyLog(date)`
	- React Query 사용: list fetch 후 date별 캐시, WebSocket 수신 시 `setQueryData` prepend, 200건 초과 trim
	- 낙관적 업데이트: Quick Logger/Routine/GH/Survey 액션 시 optimistic add → 실패 시 롤백 + 토스트
	- invalidate 규칙: 성공 시 `invalidateQueries(opsLogKeys.list(date))`

- **UI 컴포넌트**

- **폼 검증/UX**
	- 필수 필드: date, category, action_code, meta_data 타입별 required 필드 강조
	- PII 마스킹 프런트 훅: 전화/계좌 패턴 감지 시 경고/차단
	- 파괴적 액션: 2-step Confirm 모달(ref_id 표시), 권한 부족 시 버튼 disabled + 토스트 “권한이 없습니다. 관리자에게 요청하세요.”
	- 오류 노출: 4xx 필드 에러는 인라인, 5xx/네트워크는 글로벌 토스트; 멱등 충돌(200) 시 “이미 기록됨” 배지

- **테스트(E2E/컴포넌트)**

## 0. 공통 정렬 원칙
- Canonical Admin API: `/admin/api/*` (레거시 `/api/admin/*`는 미들웨어 alias만 허용)
- action_code ↔ endpoint ↔ Query Key(React Query) ↔ 테스트 케이스를 동일 표로 관리 (`action_code`가 1차 SoT)
- 멱등키 `ref_id` 필수: 지급/발송/배치/토글/Import bulk
- Immutable 로그: 수정/삭제 대신 `CORRECTION` 추가 로그만 허용

## 3. 데이터/메타 스키마
- **스키마 정의/파일**: `app/schemas/ops_log.py` 또는 별도 `app/schemas/ops_meta.py`에 JSON Schema 매핑 선언
	- 타입별 스키마: `PAYOUT`, `SYSTEM_EVENT`, `CS_DM`, `MARKETING_BROADCAST`, `SEGMENT_ACTION`, `SURVEY`, `EXPERIMENT_AB`, `JACKPOT_EVENT`, `LOSS_RECOVERY_PAYOUT` (문서 예시와 동일 필드 강제)
	- `schema_version` optional 필드 포함, 기본 1

- **검증 로직**
	- 입력 시 `action_code → meta_type` 맵 필수; meta_type 미지정 시 action_code prefix로 유추, 미스매치 시 422
	- JSON Schema validation 수행 후 PII 마스킹 훅 적용(전화/계좌/주소 정규식)
	- `ref_id` 존재 시 중복 생성 금지 + 기존 레코드 반환(멱등), 로그 메시지에 ref_id 포함

- **PII/민감정보 처리**
	- 금칙 패턴: 전화번호(010-xxxx-xxxx), 계좌, 이메일, 주소 키워드; 발견 시 저장 차단 또는 `***` 마스킹
	- meta_data에 PII 저장이 필요한 예외 케이스는 허용 목록(whitelist)로 별도 관리

- **kpi_snapshot 규칙**
	- `OpsDailyLog.kpi_snapshot`은 마감 시점에만 덮어쓰기(append 금지), 키 최소 세트(DAU, Revenue, 참여 수 등) 문서화

- **테스트(데이터/스키마)**
	- action_code ↔ meta_type 매핑 테스트: 잘못된 조합 422
	- 각 meta_type 필수 필드 누락/형식 오류 422
	- PII 패턴 포함 시 차단/마스킹 동작 검증
	- schema_version 생략 시 기본 1 설정 확인

### UI 스모크(브라우저) — 낙관적 업데이트/롤백 확인

목표: `/admin/ops`에서 4개 액션이 **즉시 prepend(optimistic)** 되고, 실패 시 **자동 롤백**되는지 확인.

1) 사전 조건
- 날짜를 오늘로 맞추고, 우측 필터에서 **분류=전체**로 둡니다(필터가 걸리면 의도적으로 optimistic 삽입을 스킵할 수 있음).

2) 성공 케이스(즉시 prepend + 서버 응답 치환)
- 좌측 패널 4개를 각각 1번씩 저장/기록합니다.
	- 빠른 운영 기록(Quick Logger)
	- 루틴 트래커(Routine Tracker)
	- 골든 아워 패널(Golden Hour)
	- 설문/DM 패널(Survey/DM)
- 우측 목록 최상단에 **즉시 새 항목이 먼저 붙는지** 확인합니다.
- 잠시 후 서버 응답이 오면 **임시 항목이 실제 항목으로 치환**되고, 중복(2개)으로 남지 않는지 확인합니다.

3) 실패 케이스(롤백)
- 빠른 운영 기록에서 `행동 코드(action_code)`를 허용되지 않는 값(예: `INVALID_TEST_CODE`)으로 입력 후 저장합니다.
- 우측 목록에 잠깐 나타났다가 **곧 사라지는지(rollback)** 확인합니다.
- 토스트/에러 메시지로 “기록 실패/허용되지 않는 action_code”류가 노출되는지 확인합니다.
