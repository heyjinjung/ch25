# ✅ 도파민04 백엔드 구현 작업 진행 체크리스트

**작성일**: 2026-01-14
**목적**: 도파민04(리텐션 장치) 구현을 “누락 없이, SoT 위반 없이, 운영 리스크 최소화”로 진행하기 위한 백엔드 체크리스트.

---

## 0) 고정 전제 (절대 변경 금지)

- **Vault SoT**: `user.vault_locked_balance`
- **Ticket SoT**: `user_game_wallet` (`GameTokenType`별 balance)
- **Inventory SoT**: `user_inventory_item`
- **스트릭 보상**: **수동 Claim 유지** (`claimable_day` 기반 UI)
- **Ticket-Zero 정의**: (기본 3종 티켓 + TRIAL_TOKEN) 합이 0
  - 키(`GOLD_KEY`, `DIAMOND_KEY`)는 입장권이지만 **Ticket-Zero 구제 대상에서 제외**

## 2) 도파민04 범위 분해 (구현 단위)

### 2.1 Ticket-Zero / Bailout(구제)

**목표**: 티켓 0 이탈을 “차단”이 아니라 “재진입”으로 전환.

- [x] Ticket-Zero 판정 기준을 백엔드/프론트가 동일하게 공유
  - (권장) 서버 응답에 `ticket_count` 또는 wallet breakdown 제공(이미 `vault/status`에 `ticket_count` 존재)
  - (확인) `ticket_count`가 **TRIAL_TOKEN 포함 합**인지(또는 3종 티켓 합인지) 정확히 문서화하고 프론트/백엔드가 동일 기준을 사용
  - (필수) 판정 대상 토큰: `ROULETTE_COIN`, `DICE_TOKEN`, `LOTTERY_TICKET`, `TRIAL_TOKEN`
- [x] Trial grant 정책을 “자동 지급”에서 “요청 기반(CTA 클릭)”으로 운영할 수 있게 유지
  - API는 `POST /api/trial-grant`로 유지하되, 호출 주체는 프론트 CTA로 제한
  - 체크 포인트: `enable_trial_grant_auto` 설정값 동작 확인(기본값이 True일 수 있으므로 운영 정책에 맞게 문서/설정 정리)
- [x] Trial grant 안전장치(어뷰징 방지) 유지/강화
  - [x] 일일 총량 캡(KST): `TrialGrantService._daily_total_cap` (현재 3)
  - [x] 허용 토큰 제한: 3종 티켓 + `TRIAL_TOKEN`만 허용
  - [x] ledger 멱등 라벨: `label = TRIAL_{token}_{YYYY-MM-DD}` (KST)
  - [x] `meta.source == "ticket_zero"` 기록

**DoD(완료 기준)**
- Ticket-Zero 상황에서 유저가 “게임 완전 불가”가 아닌 “재진입 버튼”을 반드시 갖는다.
- Trial grant는 DB ledger로 추적 가능하며, 하루 캡을 초과할 수 없다.

### 2.2 Daily Mission(원픽 카드) 지원

**목표**: 미션이 ‘숙제 리스트’가 아니라 ‘오늘의 원픽’으로 작동.

- [x] 미션 조회 응답이 “오늘의 원픽 후보”를 만들 수 있는 필드를 제공
  - (예) `logic_key` 기반으로 특정 미션(예: daily gift)을 상단 고정하는 프론트 패턴과 충돌 없는지 확인
  - (B안 고정) **원픽 선택은 프론트가 수행**: `GET /api/mission` 결과에서 1개를 선택(백엔드는 미션 데이터만 제공)
- [x] 미션 claim은 반드시 멱등/레이트리밋 적용
  - 구현 위치: ([app/api/routes/mission.py](app/api/routes/mission.py))
  - [x] `X-Idempotency-Key` 필수 유지
  - [x] 429 발생 시 detail/클라이언트 UX가 깨지지 않는지 확인

**DoD(완료 기준)**
- 미션 claim 2회 클릭/재시도로 중복 지급이 불가능하다.

### 2.3 Streak(수동 Claim) + 보이는 보상

**목표**: 스트릭은 “수동 Claim”을 유지하면서, 보상이 티켓/다이아 등 즉시 체감 재화로 귀결.

- [x] 스트릭 규칙은 UI Config로 운영 가능해야 함
  - API: `GET /api/mission/streak/rules` (UiConfig key: `streak_reward_rules`)
- [x] 스트릭 claim은 “대기 상태(Claimable)”를 서버가 명확히 제공
  - 반환 필드(권장): `streak_info.claimable_day`, `streak_info.streak_days`, `next milestone`
- [x] 스트릭 지급 경로 SoT 확인
  - WALLET 지급은 `GameWalletService.grant_tokens()`
  - INVENTORY 지급은 `InventoryService.grant_item()`
  - VAULT 지급은 `VaultService`의 locked balance 경로

**DoD(완료 기준)**
- 프론트는 `claimable_day`만 보고 버튼을 렌더/비활성화할 수 있다.
- claim 성공 시 지급 내역이 응답(`grants`)에 포함되어 화면 즉시 반영 가능하다.

### 2.4 D0 웰컴 → D1 리텐션 연결(온보딩 + 원픽 노출)

**목표**: 웰컴 수령 직후 “내일 다시 올 이유”를 만들 수 있도록, 백엔드는 **온보딩 상태 + 미션 데이터**를 안정적으로 제공.

- [ ] 온보딩 상태 API가 프론트 플로우를 끊지 않는지 확인
  - API: `GET /api/new-user/status` ([app/api/routes/new_user_onboarding.py](app/api/routes/new_user_onboarding.py))
  - 체크 포인트: 신규/기존 유저 구분, 웰컴 수령 여부, D1 연결에 필요한 최소 필드 제공
- [ ] 웰컴 수령(Claim) 엔드포인트의 멱등/중복 클릭 안전성 확인
  - API: `POST /api/new-user/claim-welcome` ([app/api/routes/new_user_onboarding.py](app/api/routes/new_user_onboarding.py))
  - 체크 포인트: 동일 요청 재시도 시 중복 지급 방지, 실패 시 UX가 깨지지 않는 에러 코드/메시지
- [x] 원픽 후보는 미션 API로 충분한지 확인(B안)
  - API: `GET /api/mission` ([app/api/routes/mission.py](app/api/routes/mission.py))
  - 체크 포인트: `logic_key`/카테고리/노출조건 등 프론트가 1개를 고를 수 있는 신호가 충분한지 (`is_featured` 플래그 추가 완료)
- [ ] (선택/향후) `GET /api/today-feature`가 존재하므로, 추후 원픽 SoT를 분리할 때 충돌 없는지 확인
  - API: `GET /api/today-feature` ([app/api/routes/today_feature.py](app/api/routes/today_feature.py))

**DoD(완료 기준)**
- 웰컴 수령 이후(또는 닫힘 직후) 프론트가 안정적으로 “원픽 카드”를 노출할 데이터가 존재한다.
- 웰컴 Claim 재시도/중복 클릭으로 중복 지급이 불가능하다.

### 2.5 VIP / Almost-VIP(레벨/세그먼트 기반 훅)

**목표**: VIP는 “대우받는 느낌”, Almost-VIP는 “한 끗”으로 당일 플레이를 유도.

- [ ] 레벨/XP 상태를 프론트가 조회 가능해야 함
  - API: `GET /api/level-xp/status` ([app/api/routes/level_xp.py](app/api/routes/level_xp.py))
  - 체크 포인트: 현재 레벨, 현재 XP, 다음 레벨까지 남은 XP(또는 진행률) 계산 가능 여부
- [ ] VIP 세그먼트 SoT가 어디인지 명확히 정리
  - (관리자) 세그먼트 관리/조회: `GET/PUT /admin/api/segments` ([app/api/admin/routes/admin_segments.py](app/api/admin/routes/admin_segments.py))
  - (관리자) CRM에서 세그먼트 기반 타겟팅 가능: `/admin/api/crm/*` ([app/api/admin/routes/admin_crm.py](app/api/admin/routes/admin_crm.py))
  - (유저 노출) VIP 여부를 유저 API에 포함할지 여부는 **정책 결정 필요**(필요 시 별도 작업으로 분리)

**DoD(완료 기준)**
- 프론트는 `/api/level-xp/status`만으로 Almost-VIP 카피/게이팅을 구현할 수 있다.
- VIP 세그먼트는 “관리/운영(세그먼트/CRM)” 기준으로 추적 가능하다.

### 2.6 Ops Scenarios / Macro Mission 연동(도파민04 7장)

**목표**: 운영 개입(DM/캠페인)과 제품 기능(리텐션 장치)이 같은 데이터/로그 위에서 굴러가게 만든다.

- [ ] (Sleeper) 72시간 미접속 + 금고 잔액>0 대상자 추출이 가능한지 확인
  - 조건 예시: `user.last_login_at` 기준 72시간+, 그리고 `user.vault_locked_balance > 0`
  - 참고: 비활동(미접속) 기반 로직 흔적은 서비스 레이어에 존재(예: inactive days 처리)
- [ ] (Almost VIP) 레벨 9/진행률 90% 대상자 추출 근거가 있는지 확인
  - API 기반: `GET /api/level-xp/status`로 유저 단위 상태 조회 가능
  - 운영 배치/대상자 추출은 별도 쿼리/스크립트로 처리(이번 체크리스트에서는 “가능/불가”만 확인)
- [ ] DM/메시지 전달 채널(최소 1개) 확보 여부 확인
  - (유저) 인앱 인박스 조회/읽음 처리: `/api/crm/messages/inbox`, `/api/crm/messages/{id}/read` ([app/api/routes/crm_inbox.py](app/api/routes/crm_inbox.py))
  - (관리자) CRM 메시지 생성/타겟팅: `/admin/api/crm/*` ([app/api/admin/routes/admin_crm.py](app/api/admin/routes/admin_crm.py))
- [ ] Ops 이벤트 스트리밍(선택): 운영 대시보드 실시간 피드가 필요하면 WebSocket 기반 확인
  - WS: `/ws/admin/ops/events` ([app/api/routes/ws_ops.py](app/api/routes/ws_ops.py))

**DoD(완료 기준)**
- “Sleeper/Almost VIP” 같은 운영 시나리오를 실행할 최소 수단(대상자 조건 + 메시지 채널)이 존재한다.
- 운영 개입 결과는 최소 1개 관측 지점(읽음/오픈/이벤트 로그 등)으로 추적 가능하다.
