# V2 Test Coverage Roadmap (Expanded)

이 문서는 V2 시스템의 안정성과 정합성을 보장하기 위해 우선적으로 보강이 필요한 테스트 영역 5곳의 상세 설계와 엣지 케이스를 정의합니다.

---

## 🏁 우선 보강 대상 5대 영역 및 엣지 케이스 설계

### 1. Admin Economy & Inventory
관리자의 수동 개입은 시스템 경제 모델의 '최종 방어선'입니다.

*   **기본 검증**: 강제 지급/차감 후 `User` & `V2User` 밸런스 동기화 확인.
*   **심화 엣지 케이스 (Advanced Edge Cases)**:
    *   **동시성 충돌 (Race Condition)**: 동일 유저에게 관리자 A는 10,000원 지급, 관리자 B는 10,000원 차감을 **완벽히 동시에(1ms 이내)** 요청했을 때, 최종 잔액이 원래대로 유지되는지 및 데이터 유실 여부. (`SELECT FOR UPDATE` 등의 락 메커니즘 검증)
    *   **잔액 부족 상황의 강제 차감**: 유저 잔액이 5,000원인데 10,000원 차감 요청 시, 시스템이 -5,000원으로 기록하는지 아니면 0원으로 'Floor' 처리하는지에 대한 정책 일관성 (SoT: 0원 미만 불허 정책 준수 여부).
    *   **트랜잭션 원자성 (Atomicity)**: 지급은 성공했으나 감사 로그(Audit Log) 기록 중 에러 발생 시, 지급된 금액이 다시 롤백되는지 확인 (돈만 나가고 기록이 없는 상황 방지).
    *   **멱등성 복합 테스트**: 동일한 `request_id`로 '지급' 요청 후 바로 '조회' 요청이 섞여 들어올 때의 응답 안정성.

### 2. Global Circuit Breaker (서킷 브레이커)
지급 한도 임계치 도달 시의 시스템 자가 보호 능력을 검증합니다.

*   **기본 검증**: CLOSED -> OPEN 상태 전이 및 지급 차단.
*   **엣지 케이스 (Edge Cases)**:
    *   **Half-Open 회복**: 서킷이 열린 후(OPEN) 일정 시간 뒤 일부 요청만 허용(HALF-OPEN)하여 성공 시 다시 CLOSED로 돌아가는 전체 생명주기.
    *   **이벤트별 격리**: 특정 이벤트(예: 루렛)에서 서킷이 터졌을 때, 다른 이벤트(예: 다이스)나 관리자 강제 지급에 영향을 주는지 여부.
    *   **Redis 장애 (Failover)**: Redis 연결이 끊겼을 때 내부 인메모리 카운터 또는 DB 카운터로 즉시 Fallback 되는지 확인.

### 3. Team Battle Lifecycle
시즌 단위의 경쟁 정합성과 보상 분배의 정확성을 검증합니다.

*   **기본 검증**: 시즌 종료 시 1~3위 팀 자동 정산 및 보상 지급.
*   **심화 엣지 케이스 (Advanced Edge Cases)**:
    *   **초정밀 순위 결정 (Sub-second Ranking)**: 두 팀의 점수가 동일할 때, 마지막 득점 시간이 **1초 미만(Millisecond/Microsecond)** 차이인 경우 이를 정확히 정렬하여 '먼저 도달한 팀'을 판별할 수 있는지 확인. (DB 타임스탬프 정밀도 검증)
    *   **정산 직전 버저비터 (Buzzer Beater)**: 시즌 종료 시각(예: 23:59:59.999)에 딱 맞춰 들어온 점수가 정산에 포함되는지, 혹은 다음 시즌으로 밀리는지에 대한 경계값 정합성.
    *   **대규모 동시 정산 부하**: 수만 명의 팀원이 동시에 보상을 수령할 때의 DB Lock 경합 및 보상 중복 지급 방지.
    *   **시즌 데이터 아카이빙**: 정산 완료 후 active 시즌 전환 시, 이전 시즌 데이터가 읽기 전용으로 안전하게 보존되는지 확인.

### 4. Golden Worker & Background Tasks
비동기 영역은 디버깅이 어렵기 때문에 시뮬레이션 테스트가 필수적입니다.

*   **기본 검증**: 리엔지먼트 이벤트 발생 시 Redis 큐 적재 및 워커 소비.
*   **엣지 케이스 (Edge Cases)**:
    *   **상태 불일치 (Stale Data)**: 워커가 큐에서 작업을 꺼냈을 때, 유저가 이미 그 사이에 입금을 하여 제재 대상에서 벗어난 경우(Skip 로직).
    *   **워커 충돌 (Crash recovery)**: 작업을 수행 중인 워커가 강제 종료되었을 때, 해당 작업이 '처리 중' 상태로 고립되지 않고 다시 큐로 돌아가는지(Visibility Timeout).

### 5. User Consistency Scripts
검증 시스템 자체가 잘못된 결과를 내놓지 않도록 하는 '검증의 검증'입니다.

*   **기본 검증**: `user_consistency_check.py` 실행 시 정상 데이터에 대해 Zero-Error 보고.
*   **엣지 케이스 (Edge Cases)**:
    *   **Orphan Mapping**: `User` 테이블에는 존재하나 `V2User`에는 없는 유저(이관 누락) 발생 시 탐지 속도 및 정확도.
    *   **미세 소수점 오차**: 정산 로직의 차이로 인해 1원 미만의 오차가 발생했을 때 이를 오탐으로 볼지, 정합성 위반으로 볼지에 대한 임계치(Threshold) 테스트.

## 🧒 중학생도 이해하는 "이게 왜 중요하고 왜 충돌하나요?"

쉽게 설명하자면, 우리가 만드는 시스템은 **'거대한 자동 정산기'**와 같습니다.

1.  **관리자 경제 (Admin Economy) 충돌**: 
    *   **상황**: 선생님(관리자) 두 분이 동시에 한 학생에게 상점 벌점 10점을 깎고, 상점 상점 10점을 동시에 주려고 합니다. 
    *   **왜 충돌하나요?**: 컴퓨터가 너무 빠르면 **"원래 점수를 읽어오기 -> 계산하기 -> 다시 적기"** 과정이 겹쳐버립니다. 두 분이 동시에 "원래 점수는 100점이네!" 하고 읽어가서, 한 분은 90점으로, 한 분은 110점으로 적으려다보니 마지막에 적은 사람 것만 남고 한 사람의 작업은 증발해버릴 수 있어요. 이걸 막는 게 **'동시성 제어'**입니다.

2.  **팀 배틀 (Team Battle) 충돌**:
    *   **상황**: 이어달리기 결승전에서 두 팀이 거의 동시에 들어왔습니다.
    *   **왜 충돌하나요?**: 우리 눈에는 동시에 보이지만, 초정밀 카메라(서버)로 보면 **0.001초 차이**가 날 수 있어요. 만약 카메라가 "둘 다 14시에 들어왔음"이라고만 기록하면 싸움이 나겠죠? 그래서 아주아주 정밀한 시계(타임스탬프)를 써서 누가 0.1mm라도 먼저 들어왔는지 가려내야 합니다. 이게 안 되면 1등 상품이 엉뚱한 팀에 갈 수 있으니까요!
